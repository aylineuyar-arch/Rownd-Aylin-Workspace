# Changelog

Every push to this repo is logged here, newest first, in plain language — what changed and why. This file is updated as part of every commit from now on, not just written after the fact.

## 2026-09-10

- **Added a real "Create Folder" feature to the archive panel** — after being asked where it was three separate times, built it directly into the app instead of continuing to point back to Finder. `serve_no_cache.py` gets a new `POST /archive-mkdir`, gated by the same session cookie as everything else, validating the name is a single plain path segment (no `/`, no `..`/`.`, no leading dot, ≤200 chars) so directory traversal outside the archive folder is structurally impossible, not just discouraged. Also removed the "set or change this from the terminal..." line from the password box — not something the page needs to explain. Along the way, found and fixed a real bug the new feature immediately exposed: the listing only ever showed files, so creating an empty folder gave zero visual confirmation — it just kept showing "No files found," indistinguishable from doing nothing at all. `walkArchiveDir` now also tracks folders it encounters, and they render with a "DIR" badge, linking to their own listing. Verified the whole path with curl (unauthenticated mkdir → 403; valid name → 200, folder actually appears on disk; `../../etc/evil` and `../escaped` → both rejected, nothing created outside the archive; duplicate name → 409; dotfile-style name → 400) and in the real UI (created a folder through the page, watched it appear immediately with a working link, folder count no longer silently indistinguishable from empty).
- **Also fixed 2 bugs found in a second review pass**: `_read_bounded_body()` (shared by both login and mkdir) now catches `socket.timeout` during the body read instead of letting it propagate uncaught if a client stalls mid-request. The recursive folder walk and per-file size lookups fanned out via `Promise.all` with no cap — a wide/deep archive could fire an unbounded number of simultaneous fetches; added `mapWithConcurrencyLimit` (batches of 4) and used it in both places, so they're still parallel, just bounded. Re-verified the full regression sweep afterward: existing nested folders, files, and sizes all still render correctly, and a freshly-created folder still shows up immediately.



- **Security review pass on the archive server/client — found and fixed a real full-server DoS, plus four smaller bugs.** Ran a systematic review (correctness, reuse, efficiency, robustness) on `serve_no_cache.py` and the archive JS, the same class of bug-hunting that caught the Basic-Auth issue earlier. The serious one: `POST /archive-login` read `Content-Length` with no validation and passed it straight to `self.rfile.read(length)` — a negative value makes that call block until the connection closes, and since this is a plain single-threaded `HTTPServer`, that **freezes the entire server for every client**, not just the bad request. Confirmed by reproducing it directly: one malformed request left the server completely unresponsive for 120+ seconds until killed. Fixed two ways — validated Content-Length is a sane non-negative, bounded value (max 4096 bytes, far more than any real password needs) before reading, and added `timeout = 10` on the handler class so *any* stalled read on a connection times out instead of blocking forever (the general fix, not just this one call site). Also fixed: `_needs_auth()` now fails closed (requires auth) instead of raising an uncaught exception if path resolution ever errors; a duplicate `formatFileSize()` function was removed in favor of the existing `formatSize()` already used elsewhere; per-file size lookups and subfolder listings now fetch in parallel (`Promise.all`) instead of one at a time; and the archive listing no longer silently hides every file/folder starting with a dot — only our own `.gitkeep` is excluded, so a real file never vanishes without explanation. Re-verified the DoS fix by firing the exact request that previously hung the server (now an instant 400, server stays responsive) and re-verified the dotfile/nested-folder/parallel-fetch behavior with real test files.



- **Replaced HTTP Basic Auth with a real session-cookie login — Basic Auth's native browser dialog turned out to be unreliable.** Watching the actual traffic in a real browser session, a single blocked page load produced over 30 identical requests to `/private-rfi-archive/`, all still returning the correct 401 — the server was fine, but the browser's own native Basic-Auth negotiation was retrying in a tight loop trying to resolve credentials, even with an explicit (wrong) `Authorization` header already attached, and the fetch sometimes failed outright instead of resolving. That's specifically caused by responding 401 with a `WWW-Authenticate` header, which is what tells a browser to attempt that native negotiation at all. Removed it entirely: `serve_no_cache.py` now exposes `POST /archive-login` (checked against the same SHA-256 password hash, `hmac.compare_digest`), which on success sets an HttpOnly, session-only cookie; every request after that — including a plain click on a file's "Open" link, not just this page's own fetch calls — carries it automatically, because that's just how cookies work, with zero native dialog ever entering the picture. A denied request is a plain 403 with no `WWW-Authenticate`, so there's nothing left for a browser to "negotiate." Added a real password box directly in the Reference Documents page (replacing the reliance on the browser's own prompt). Verified in an actual browser: one login attempt now produces exactly one request (not 30+); wrong password shows an inline error; correct password reveals the real listing; and — the specific thing the cookie design was chosen to guarantee — a plain link click to a file works via the auto-attached cookie (checked directly: the same request with credentials explicitly omitted gets 403, confirming the cookie is really what's gating it).



- **Removed the three fake placeholder documents from Reference Documents** — "Company Capability Statement," "Embedded Systems Architecture Diagram," and "Past Performance Boilerplate" were leftover static mock content from the original UI mockup, sitting right below the real Private RFI/RFP Archive panel and easy to mistake for real data. The reference-upload zone above them is untouched. Verified via the sandbox: all three are gone from the page text, the archive panel and upload zone both still render.



- **Private archive: collapsible privacy policy, and real folder support.** The always-visible security explanation on the archive panel was pushed behind a "View privacy policy" toggle (same chevron pattern used elsewhere), leaving just a one-line description visible by default. Separately, the listing only ever looked at the top level of `private-rfi-archive/`, so a file organized into a subfolder was invisible — create folders however you like on disk (Finder's "New Folder" works fine, no new upload code needed) and the app now recurses into them (`walkArchiveDir`, capped at 6 levels deep) and lists every file it finds with its folder path shown (e.g. `SBIR-25-101/company-response.pdf`), instead of only what's sitting loose at the root. Verified with a real nested test file: confirmed the server's auth still covers the nested path with no code changes needed (containment check from the last fix already generalized correctly), and confirmed the recursive walk found both the top-level and nested file with a correctly-encoded, working link to each.



- **Found and closed two real auth-bypass bugs in the archive server, by deliberately trying to break it.** The previous fix checked the raw request path as a literal string prefix — but `curl http://localhost:8740/Private-RFI-Archive/file.pdf` (different case) and `curl http://localhost:8740/private-rfi-archive%2Ffile.pdf` (URL-encoded slash) both returned **200 with no credentials at all**, because macOS's default filesystem is case-insensitive and the server's own file-serving logic decodes `%2F` before opening the file — both happening *after* my naive string check had already decided "not protected." Fixed by resolving the request through the exact same `translate_path` + `os.path.realpath` logic the server uses to decide what file to actually open, then checking real containment inside the archive folder (`os.path.commonpath`) instead of comparing raw strings — so whatever encoding or case a request uses, the auth decision and the file-serving decision can no longer disagree. Re-verified with a curl battery: baseline, case variant, encoded slash, double slash, dot-segment traversal, and case+encoding combined — all correctly 401 without credentials, all correctly 200 with the right password, directory listing and individual files both covered, and the non-archive part of the site still needs no auth at all. Also re-confirmed the loopback-only binding survived the rewrite (LAN access still connection-refused).



- **Fix: the private archive had a real network-exposure hole, and the first password gate was fake security — replaced both with server-enforced protection.** `python -m http.server` (and my earlier `serve_no_cache.py`) binds to all network interfaces by default, not just this machine — confirmed with `lsof` that it was listening on `*:8740`, meaning anyone else on the same WiFi/LAN could have browsed straight to `private-rfi-archive/` with zero login. Separately, a first pass at "password protection" checked the password in the page's own JavaScript (hash in localStorage) — that protects nothing, since a direct request (curl, another tab, another device before the fix above) never goes through that JS at all. Replaced both: `serve_no_cache.py` now binds to `127.0.0.1` only (confirmed via `lsof` and a real cross-check — a request to the machine's LAN IP now gets connection-refused, exit code 7), and enforces real HTTP Basic Auth on `/private-rfi-archive/*` at the server level, checked with `hmac.compare_digest` against a SHA-256 hash stored in `Rownd/.archive_auth_hash` (git-ignored, chmod 600) — a 401 with `WWW-Authenticate` that no page-level trick bypasses, because the page's JS is never in the request path. The archive folder is also now `chmod 700` (OS-level, owner-only). Verified the full matrix with curl: no credentials → 401, wrong password → 401, correct password → 200, on both the directory listing and individual files; confirmed the regular (non-archive) pages still serve with no auth needed. The password is set interactively (`getpass`, never echoed, never logged) the first time the server runs, or via an `ARCHIVE_PASSWORD` env var for scripted runs — either way it's hashed before it touches disk, and it's never in a file this repo tracks.



- **Private, local-only RFI/RFP archive** — previously-sent RFI/RFPs will be the basis for future generated proposals, and are highly sensitive, so they needed to live somewhere that's structurally impossible to push to this public repo. Added `Rownd/private-rfi-archive/` for real files, protected by a new root `.gitignore` (`Rownd/private-rfi-archive/*`, with only `.gitkeep`/`README.md` excepted so the folder itself stays discoverable). Verified directly: dropped a file with sensitive-looking content into the folder, confirmed `git status`/`git add -A` never sees it, confirmed `git check-ignore` matches it. Added a "Private RFI/RFP Archive" block to the Reference Documents page that lists whatever's actually in that folder (using the dev server's own auto-generated directory listing — no manifest file, no server code of ours) and links each file to open/preview it. On the deployed GitHub Pages site the folder doesn't exist, so this correctly shows an "unavailable" state instead of an error — verified both the empty-folder and populated-folder states, and confirmed a fetch to a nonexistent path 404s the way Pages will.



- **Checklist text boxes now grow to fit their content — no internal scrollbar.** They previously had a fixed min-height with `resize-y`, so pasted or extraction-filled text beyond that height was hidden behind a scrollbar inside the box. Switched to auto-grow: each box's height now tracks its own content on every keystroke/paste, and also when extraction programmatically fills a box (Phase I text into Solicitation instructions, etc.), since that already dispatches the same `input` event. Verified with a long pasted block (grew to 9176px, no internal scroll) and with extraction-filled text (grew from 132px to 3156px automatically).

## 2026-09-09

- **Fix: PDF uploaded to the top "reference files" zone did nothing** — the New Draft page has two upload zones that look nearly identical: the top "Drop reference files" box and the "RFI details" box inside the Draft Checklist. Only the checklist one was ever wired to run extraction; the top one just attached the file to a list and stopped there, so a topic PDF dropped in the wrong-looking-right zone silently produced no Extracted Topic Info. Fixed by having the top zone forward any PDF it receives into the same extraction pipeline (and check off the RFI details checklist item), so it works from either zone now. Verified with a synthetic PDF against both zones before and after.

- **Also found: the local dev server (`python -m http.server`) sends no cache headers, so the browser was serving stale cached copies of `index.html` after edits** — this is the likely real explanation for at least one earlier "reload the page, it's showing the old version" report. Replaced it with `Rownd/serve_no_cache.py`, a thin wrapper that adds `Cache-Control: no-store` to every response, so a normal reload always gets the current file. Run it the same way: `python3 serve_no_cache.py 8740` from inside `Rownd/`.
